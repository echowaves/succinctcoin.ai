Deep Recon · Technical Research

Equal-node JS cryptocurrency architecture

Type technicalStatus complete Preset standardValidation normal Created 2026-09-29Updated 2026-09-30 Claims 35 verified · 28 unverified · 0 overturned
Decision this research serves: the consensus + networking architecture for a JS cryptocurrency where every running node has an equal chance to mine (no ASIC, no stake advantage), simple enough that any developer can understand it — JS, libp2p, Electron + React, big.js, properly tested.

Executive summary

  1. Consensus — slot-paced low-difficulty PoW on native sha256, per-slot identity tickets, non-scaling registration cost. The deep dive's headline is an absence: no deployed coin delivers true P≈f(uptime) — every live family uses a parallelizable resource, which 2026 theory shows makes N-identity Sybil at near-zero cost [D1.1]. The fix is in the registration economics (an entry cost capping odds at 1× per operator without scaling the reward) — no deployed system fills that gap [D1.9] — and the D6 deepening now proposes the mechanism: a Bounded Participation Channel (per-slot re-verification, τ per operator) behind a one-time personhood gate [D6.5][D6.14]. Low-difficulty PoW is the simplest family to implement and unit-test in JS [D1.12]; native sha256 (measured 3 GB/s) makes one-hash-per-slot trivially reachable [D5.1]. Avoid VDF time anchors: Ethereum abandoned its Minroot-VDF plan after a discovered attack [D1.5].
  2. Networking — tcp + noise + yamux + gossipsub; static bootstrap at genesis, mDNS for LAN, DHT deferred; circuit-relay v2 for desktop nodes behind home NATs. All current, production-proven js-libp2p 3.3.11 components [D2.1][D2.5][D2.15]. Bonus: a first-party electron-main test target [D2.18] and a socket-free memory transport [D2.16] make the network layer testable in CI and in the app.
  3. Shell + bundler — Electron main process hosting a pure-Node core package; Vite 8 (Rolldown) for the React UI. Electron's main process is Node, so core, shell, and tests share one language and one test suite — the biggest "any developer can understand it" win. Tauri v2 is the named runner-up if bundle size/RAM becomes a hard gate (needs Rust + a Node sidecar; size numbers directionally solid but unverified) [D3.5].
  4. Money — big.js on the ledger path only. Measured: big.js plus ≈ 8.6M ops/s but times ≈ 10.9K ops/s — ~1000× slower — so the PoW/fee hot loop stays on node:crypto + integer counters, big.js materializes only when a block's balances commit [D5.4][D5.5]. Testing: plain-Node unit tests (no shell, no network) + fast-check property tests over ledger invariants.

Biggest caveat: the equal-node guarantee is only as strong as the registration/sybil-cost design — the project's novel contribution. D6 now proposes the concrete form (one-time personhood gate + per-slot BPC ticket + uptime election), but it rests on single-group 2026 preprints and has no deployed precedent; it needs a spec + attack pass before launch (Open question #1). Everything else is solved, standard, and verified.

D1 · Equal-chance-per-node consensus (deep dive)

The property, precisely: P≈f(uptime), not f(hashrate) and not f(stake). Headline: no deployed system could be evidenced that delivers it. Every live family weights by a parallelizable resource — and 2026 theory formalizes why that fails the property: "can be subdivided across many identities at negligible marginal cost, making linear Sybil cost fundamentally unattainable" [D1.1].

Attack ordering for equal-node designs [D1.8][D1.9]: (1) Sybil/identity duplication IS the 51% path — no hashrate floor; (2) long-range is worse than in Bitcoin — no accumulated work anchors history, and VDF anchors are risky (Ethereum abandoned Minroot-VDF [D1.5]); (3) selfish mining: Eyal–Sirer finds the vanilla-Bitcoin profitability threshold is close to zero (1/3 bound), while the often-cited 25% is the threshold of their proposed fix — plan for "small pools can profit," not "only 25%+ pools". The open design point: a non-scaling sybil-cost entry (caps odds at 1×/operator, doesn't scale reward) — no deployed system uses one; stake-weighted lotteries have a documented compounding ratchet [D1.11].

D2 · libp2p networking for a small node

Recommended minimal stack (2026): js-libp2p 3.3.11 (2026-09-02, 392 dependents on npm, production in Lodestar/Helia/HOPR/OrbitDB) [D2.1][D2.5]. Examples' Node default: tcp + noise + yamux [D2.2]; floodsub "not suitable for production" → gossipsub [D2.3]. Legacy components carry no npm deprecated flag — deprecation lives in docs only [D2.4].

Bootstrap + discovery (10 → few thousand nodes) — three documented layers [D2.8]: static bootstrap list [D2.6] → mDNS (LAN) [D2.7] → Kad-DHT (deferred; no documented node-count threshold). NAT traversal: circuit-relay v2 is the documented behind-NAT pattern [D2.11]; WebSockets the outbound-only workaround [D2.12]; WebRTC/WebTransport exist but NAT behavior unverified [D2.13] (no production NAT docs retrievable [D2.14]). Testability: @libp2p/memory = socket-free full-stack tests [D2.16]; multidim-interop conformance suite [D2.17]; first-party electron-main test target (verified, contradiction resolved — lives in @libp2p/utils) [D2.18].

The reframe: js-libp2p's @libp2p/tcp and @libp2p/mdns are Node-only — a full node is a Node.js process regardless of shell [D3.1]. The shell is a UI client on top of a Node core.

D4 · JavaScript as a blockchain language

The precedent: Lodestar — production TypeScript Ethereum PoS consensus client on Beacon Chain mainnet [D4.1], actively maintained (v1.49.0, 2026-09-28) [D4.2], and the only TypeScript entry in ethereum.org's consensus-client table [D4.5]. That one project proves a JS node can do sync/libp2p/consensus/24-7-storage at real-chain scale.

What the JS node offloads: everything in TS except the crypto hot path — consensus-critical crypto runs through native Zig modules (lodestar-z, NAPI), compression → WASM, networking → worker threads [D4.3]. No documented JS mining hashrate exists [D4.11]. Implication: keep the per-attempt hash in native node:crypto with a JS/BigInt counter. Counter-evidence, honestly: the JS execution layer never reached production (EthereumJS client is beta/testnet-only [D4.6]); no "JS failed" incident found, no two-source failure claim asserted [D4.13]; bcoin npm frozen 2018 (caution flag [D4.9]); HOPR status unresolvable this run [D4.10]. Settled toolchain (two projects agree): TypeScript + Vitest, pnpm + Node 24 [D4.12].

Load-bearing: (a) big.js multiply is ~1000× add — a structural O(n·m) property [D5.5]; (b) native sha256 is ~35× cheaper per byte than pure-JS keccak — a sha256-based mining hash fits "simple JS + low difficulty" [D5.2]; (c) exactness is the reason for big.js: 0.1+0.2 is 0.30000000000000004 in float but "0.3" in big.js [D5.8]; JSON.stringify(Big)→string, JSON.stringify(BigInt) throws [D5.6]. Design consequence: big.js on the ledger path only, never the PoW hot loop [D5.9]; integer base-units (BigInt) for bulk [D5.10]; plain-Node + fast-check property tests for ledger invariants [D5.11].

D6 · The registration design (deep dive — the novel open question)

Headline: 2026 preprint theory pins down what a non-scaling entry cost requires — a throughput-bounded, non-transferable, window-local resource — and proves money/compute/storage are all amortizable (C(s,T)=o(sT)) so they can't be the cost basis [D6.2][D6.4]. The one mechanism with a provable linear cost floor is the Bounded Participation Channel: re-verify every identity with a fresh, identity-bound, real-time, throughput-bounded challenge every slot — C(s,T) ≥ sT/τ_h [D6.5]. No deployed system uses it: closest are one-time proof-of-personhood (World ID, BrightID) and refundable stake-scaled PoS bonds [D6.10][D6.11][D6.12].

Why a plain fee/deposit fails: money has all four forbidden parallelizability properties — it splits across 1,000 identities, reuses across windows, transfers between them, and influence is additive in it. Once bought, marginal cost vanishes; concave fee→power mappings still show 1,172×–4,039× Sybil amplification under Quadratic Voting [D6.2][D6.9].

Recommended composition (DESIGN, to carry to a spec) [D6.14]: (1) one-time personhood gate (World-ID-style or open social-graph) mints one base identity per operator → flat, non-buyable entry; (2) per-slot BPC ticket — fresh identity-bound proof within the slot window over a channel with τ per operator, not per identity → marginal survival cost positive; (3) uptime-weighted election among valid tickets → P≈f(uptime) within the capped set. Must-holds: τ per-operator; window-local (no carry-over); pluggable gate; stop re-verifying → lose eligibility.

Honest caveats: D6.2–D6.4 are single-group 2026 preprints (unpeer-reviewed); the BPC AI numbers are the authors' own eval [D6.6]; Gitcoin Passport + VDF-for-registration specifics were not verifiable this run [D6.13]. Theoretically grounded, not yet deployed — spec + attack pass before launch is still mandatory.

Cross-dimension insights

  1. The "equal node" requirement and the JS runtime converge on the same architecture. D1 (per-identity scarce resource) + D5 (native hash, big.js out of the hot loop) + D4 (production JS client offloads crypto) all point to: slot-based election + native sha256 + identity tickets, JS/TS owning state/networking/accounting.
  2. The desktop shell is the cheapest decision — if the core is a pure Node package. D3's zero-UI-imports seam is what makes D2's electron-main target and D4's Vitest toolchain both apply.
  3. Sybil cost is the coin's economic design, not its consensus code. The hard, novel work is the registration/economics spec — not the hashing or networking, which are solved.
  4. Network size sets discovery complexity. bootstrap + mDNS (+ DHT if needed) and look-back k=40–70 are both sized for a small, mostly-stable peer set.

Recommendations

  1. Consensus: slot-paced low-difficulty PoW (sha256), per-slot identity tickets, non-scaling registration cost. medium — mechanism standard; equal-node guarantee rests on novel registration economics.
  2. Long-range anchoring: keep a PoW-like work anchor; do not use a VDF. medium-high — D1.5 single-sourced; double-source Buterin blog + ACM cryptanalysis.
  3. Networking: tcp + noise + yamux + gossipsub; static bootstrap, mDNS, DHT deferred; circuit-relay v2 for NAT. high for components, medium for NAT story.
  4. Shell + bundler: Electron main process hosting a pure-Node core; Vite 8 (Rolldown); core = packages/core, zero shell imports. high (Tauri size unverified).
  5. Money: big.js on ledger path only, integer base-units for bulk, native sha256 + integer counter in the PoW loop. high (self-measured).
  6. Testing: plain-Node unit tests (Vitest), @libp2p/memory for socket-free network tests, fast-check property tests for ledger invariants. medium-high

Open questions

  • What makes a second identity cost ≥ the first without scaling the reward? The coin's novel contribution; unsolved by any deployed system. Needs its own design + attack pass.
  • How many nodes before bootstrap+mDNS stop sufficing and the DHT is warranted? No documented threshold.
  • What fraction of a real chain's nodes run a JS client, and what does that do to 24/7 GC/heap at this scale?
  • HOPR's current status (second non-Ethereum TS+libp2p precedent) — unresolvable this run, all paths 404.
  • VDF abandonment double-source (D1.5) — single-sourced via IACR survey; retrieve Buterin blog + ACM cryptanalysis.
  • WebRTC host-to-host NAT behavior for desktop nodes — hypothesis only.
