### Q2 — Bootstrap + discovery for a small network

ref=[D2.6] status=unverified class=mechanism pub=2026 — **First-nodes-with-no-DHT pattern = static
bootstrap list.** `@libp2p/bootstrap({ list: [...] })` dials a fixed set of multiaddrs on boot. The
official example seeds the list from IPFS's public bootstrap peers (e.g. `/dnsaddr/bootstrap.libp2p.io/p2p/Qm...`).
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-discovery-mechanisms/bootstrappers.js
Publisher: libp2p org.

ref=[D2.7] status=unverified class=mechanism pub=2026 — **LAN discovery pattern = mDNS.** `@libp2p/mdns({
interval: 20e3 })` finds peers on the same local network with no explicit dialing; discovered peers are
stored in the PeerStore.
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-discovery-mechanisms/README.md (+ 2-mdns.js)
Publisher: libp2p org.

ref=[D2.8] status=unverified class=mechanism pub=2026 — **When you need the DHT: `@libp2p/kad-dht`**
(Kademlia / "Amino" DHT) gives both peer discovery (self-query / random walk) and peer+content routing.
Example: `kadDHT({ protocol: '/ipfs/lan/kad/1.0.0', clientMode: false })`. For a small network, the
examples frame the choice as: bootstrap (always connect) + mDNS (locality) + DHT (serendipity/routing).
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-discovery-mechanisms/1-dht.js (+ README §1)
Publisher: libp2p org.

ref=[D2.9] status=unverified class=mechanism pub=2026 — **Pubsub-based peer discovery**
(`@libp2p/pubsub-peer-discovery`, separate repo) is the documented mechanism for environments where DHT
transports (TCP/QUIC) are unavailable — explicitly called out for **browser** nodes. A small
Electron+React node with browser-capable peers would use this.
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-discovery-mechanisms/README.md (§3)
Publisher: libp2p org.

ref=[D2.10] status=unverified class=ecosystem pub=2026-08 — **`@chainsafe/discv5` = "Discovery V5"**
(Ethereum's UDP-based discovery v5 protocol). Latest **12.0.2 (2026-08-11)**, 68 published versions,
maintainers **wemeetagain + matthewkeil**. It is a UDP discovery protocol, NOT a libp2p transport; it is
warranted when you need Ethereum-style peer discovery interop (Lodestar/Chainsafe ecosystem). I could not
retrieve its usage docs within budget, so "when it is warranted for THIS project" is an inference, not a
retrieved fact.
Source: https://registry.npmjs.org/@chainsafe%2Fdiscv5
Publisher: npm registry.

### Q3 — NAT traversal reality

ref=[D2.11] status=unverified class=mechanism pub=2026 — **Documented host-behind-NAT pattern = circuit
relay (v2, `@libp2p/circuit-relay-v2`).** A public relay node runs `circuitRelayServer()` (listening on
`webSockets()` + `noise()` + `yamux()`); a NATed node adds `circuitRelayTransport()` and listens on
`'/p2p-circuit'`. README states the "typical use cases" are "nodes behind a NAT or browser nodes due to
their inability to expose a public address."
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-circuit-relay/README.md (+ relay.js)
Publisher: libp2p org.

ref=[D2.12] status=unverified class=mechanism pub=2026 — **WebSockets is the practical NAT/firewall
workaround transport** (outbound-only, works where raw inbound TCP is blocked); the circuit-relay example
uses `webSockets()` as the transport for both the relay and the NATed listener.
Source: https://raw.githubusercontent.com/libp2p/js-libp2p-examples/main/examples/js-libp2p-example-circuit-relay/relay.js
Publisher: libp2p org.

ref=[D2.13] status=unverified class=mechanism pub=2026 — **WebRTC/WebTransport** are listed as first-class
transports (`@libp2p/webrtc` 6.0.33, `@libp2p/webtransport` 6.0.40) with dedicated example dirs
(`webrtc-private-to-private`, `webrtc-private-to-public`). WebRTC's NAT traversal (ICE/STUN/TURN) is a
well-known property but I did NOT retrieve the example bodies or docs this run — treat "WebRTC works
host-to-host across NAT" as an unverified hypothesis.
Source: https://github.com/libp2p/js-libp2p (README) + https://registry.npmjs.org
Publisher: libp2p org + npm registry (existence only, not NAT behavior).

### Q5 — Testability of the network layer

ref=[D2.16] status=unverified class=mechanism pub=2026 — **`@libp2p/memory` is an in-process in-memory
transport "intended for testing"** that can only connect two libp2p nodes within the same process. It
enables unit/integration tests of the full protocol stack (transports/crypto/muxer/pubsub) with **no real
network** — the key enabler for the project's "properly covered by tests" requirement in CI without
flaky sockets.
Source: https://raw.githubusercontent.com/libp2p/js-libp2p/main/packages/transport-memory/README.md
Publisher: libp2p org.

ref=[D2.17] status=unverified class=mechanism pub=2026 — **Interop/conformance suite exists: `interop/` =
`@libp2p/multidim-interop` ("Multidimensional interop tests").** Workflow: build js-libp2p (node +
browser), build another libp2p implementation, run Redis, start both, run interop. Root script
`test:interop`. This is the cross-implementation conformance path (e.g. js-libp2p vs a Go/other impl).
Source: https://raw.githubusercontent.com/libp2p/js-libp2p/main/interop/README.md
Publisher: libp2p org.

ref=[D2.18] status=verified class=versions-compat pub=2026-09 — js-libp2p root `package.json` test
scripts are **aegir-based**: `test`, `test:node`, `test:chrome`, `test:chrome-webworker`, `test:firefox`,
`test:firefox-webworker`, `test:electron-main`, `test:webkit`, `test:cli`, `test:interop`.
**CONTRADICTION RESOLVED (lead spot-check 2026-09-30):** the earlier "does not exist" check looked at the
PUBLISHED `libp2p` npm tarball and `packages/libp2p/package.json` — both aegir-monorepo artifacts that
omit it. The repo-root `main` `package.json` does contain `"test:electron-main": "aegir run test:electron-main"`,
and the target lives in **`packages/utils`** (`"test:electron-main": "aegir test -t electron-main"`). So the
js-libp2p ecosystem has a **first-party aegir `electron-main` test environment** — a concrete signal that
running libp2p in Electron's main process is a supported, tested configuration.
Sources: https://raw.githubusercontent.com/libp2p/js-libp2p/main/package.json + https://raw.githubusercontent.com/libp2p/js-libp2p/main/packages/utils/package.json (both fetched 2026-09-30)
Publisher: libp2p org.
