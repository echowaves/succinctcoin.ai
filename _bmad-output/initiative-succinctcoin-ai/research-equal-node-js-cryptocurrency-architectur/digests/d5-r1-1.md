# D5 — big.js money + testing strategy (Round 1)

Decision served: money representation + test strategy for a JS cryptocurrency whose core
(libp2p + big.js + consensus) must be "properly covered by tests" and simple enough that any
developer can understand.

## Local benchmark — measured THIS RUN on the project machine (primary evidence)

Machine: Node v24.14.0, macOS arm64 (Apple Silicon), big.js 7.0.1, js-sha3 (pure-JS keccak).
Harness: bench/bench.js (+ bench/diag.js). Full JSON: bench/bench-results.json.

- ref=[D5.1] status=verified class=performance pub=2026-09-29 — node:crypto sha256 = 3.085 GB/s
  (512×1MB). Native, fast. Source: local bench, bench-results.json. (Single-source: self-measured,
  but it's the primary source by construction.)
- ref=[D5.2] status=verified class=performance pub=2026-09-29 — js-sha3 pure-JS keccak256 =
  0.0896 GB/s (2048×64KB) — ~35× SLOWER than native sha256. Source: local bench. => If the coin
  uses a keccak-based hash (EVM-style) in JS, pure-JS keccak is a real cost; a sha256-based PoW is
  ~35× cheaper per byte in JS. Favors a sha256-based mining hash for the "simple JS" + low-difficulty
  story.
- ref=[D5.3] status=verified class=performance pub=2026-09-29 — BigInt: 2,000,000 adds in 5.2ms
  ≈ 385M adds/s. Source: local bench.
- ref=[D5.4] status=verified class=performance pub=2026-09-29 — big.js 7.0.1 `plus` (money-sized):
  100,000 adds in 11.6ms ≈ 8.6M ops/s. `div` ≈ 4.1M ops/s. Source: local bench/diag.
- ref=[D5.5] status=verified class=performance pub=2026-09-29 — big.js `times` (money-sized,
  bounded digits): 100,000 multiplies in ~9.1s ≈ 10.9K ops/s — ~1000× SLOWER than `plus`. Source:
  local bench/diag. UNBOUNDED: 100,000 chained `times(1.001)` grew to 300,048 digits and took 106s
  (quadratic). => big.js multiply is O(n·m) over its internal digit array.
- ref=[D5.6] status=verified class=versions-compat pub=2026-09-29 — `JSON.stringify(new
  Big(123.45))` → `"123.45"` (a JSON string via Big.prototype.toJSON); `JSON.stringify(123n)` THROWS
  "Do not know how to serialize a BigInt". Source: local bench/diag. => big.js round-trips to a
  string (needs explicit string parse on read); BigInt needs a custom JSON replacer/reviver.
- ref=[D5.7] status=verified class=performance pub=2026-09-29 — serialization: 10,000 money values,
  11.8 bytes/value; JSON.stringify ×100 in 120.9ms, JSON.parse ×100 in 33.6ms. Memory (100k objects,
  RSS delta, GC-noisy): big.js ≈ 1,072KB vs BigInt ≈ 784KB (~37% bigger). Source: local bench.
- ref=[D5.8] status=verified class=architecture pub=2026-09-29 — exactness: 0.1+0.2 in float =
  0.30000000000000004; big.js = "0.3". The float trap is real; big.js removes it for +/−. Source:
  local bench.

## Implication for the design (the point of the dimension)

- ref=[D5.9] status=decision class=architecture pub=2026-09-29 — Put big.js on the LEDGER/accounting
  path (per-transaction balance add/subtract, ~8.6M/s — plenty), NEVER in the PoW/consensus hot
  loop. A per-attempt hash uses native node:crypto (sha256, 3 GB/s) with a plain integer/BigInt
  counter; big.js only materializes when a block's balances are committed. This keeps the ~1000×
  multiply penalty (D5.5) off the mining path entirely.
- ref=[D5.10] status=decision class=architecture pub=2026-09-29 — Fee = amount × rate is the one
  big.js `times` in the ledger path. At ~10.9K/s it is fine per-transaction (a block of thousands of
  txs = tens of ms) but must not be called per-PoW-attempt. Consider precomputing fee schedules as
  adds/multiplies by a constant, or store amounts in an integer base unit (sats-style) with BigInt
  for the bulk and big.js only where a fractional rate is genuinely needed.
- ref=[D5.11] status=unverified class=architecture pub=2026-09 — Testing strategy (ties to "properly
  covered by tests"): the core is a pure Node package, so the money layer is unit-tested with a plain
  Node runner (node:test or Vitest) — no desktop shell, no network. Property-based tests (fast-check)
  over the big.js ledger ops (add/subtract/fee invariants, no-negative-balance, conservation of
  supply) are the high-value layer because they encode the "simple enough to understand" invariants
  as executable specs. (Strategy is a recommendation, not a retrieved fact — flagged unverified.)

## What I looked for and could not find
- No third-party big.js benchmark found that isolates `times` vs `plus` at money-sized digit
  lengths — the ~1000× ratio is self-measured here; treat the absolute ratio as machine-specific but
  the direction (multiply ≫ more expensive than add) as a structural property of big.js's O(n·m)
  digit-array multiply. Did not benchmark decimal.js or bignumber.js for comparison (scope: the
  user fixed big.js).

## Leads worth chasing
1. decimal.js vs big.js vs bignumber.js multiply throughput — if the ~10.9K/s `times` ever bites,
   bignumber.js/decimal.js have different internal bases; a 30-min comparison bench would settle it.
2. fast-check property-based tests for a big.js ledger — concrete example codebase if one exists.
3. Whether to store the ledger in integer base-units (BigInt, 385M adds/s) with big.js only for
   fractional-rate fees — a concrete serialization + hot-path decision for the architecture spine.
